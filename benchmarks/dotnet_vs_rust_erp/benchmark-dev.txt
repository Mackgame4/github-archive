WHY RUST IS SLOWER CONCURRENT IN SQLX:

Concurrency adds several factors:
- Your Rust pool permits five database connections, while we benchmarked eight clients. Requests can queue for connections.
- Several SQLite workers and async tasks are simultaneously producing, transferring, and decoding rows. Scheduling and synchronization costs can grow.
- Rust still validates domain objects and copies strings into DTOs. We optimized C# to materialize DTOs directly.
The five-connection limit alone does not establish an explanation for a 17× throughput gap. Likewise, our phase diagnostic groups database execution, SQLx decoding/transfer, and domain construction together. It identifies the slow region, not the precise culprit.
Your setup therefore matters, but we haven’t demonstrated that Windows or your hardware is defective. Laptop variability affects timings; the repeated concurrency gap deserves a controlled driver comparison.
My earlier recommendation needs that qualification: we established that your current C# implementation handles this workload better—not that Rust inherently handles concurrency worse.
The next useful experiment is the same Rust query using SQLx with different row-buffer sizes, then rusqlite with the whole query executed inside a bounded blocking worker, keeping connection limits, mapping, and payloads comparable. That would distinguish SQLx overhead from application overhead much more convincingly than another unchanged API benchmark.
